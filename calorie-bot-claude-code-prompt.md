# Задача: Telegram-бот для подсчёта КБЖУ + клетчатки (Java / Spring Boot)

Ты строишь проект с нуля. Работай по этапам из раздела «План», после каждого этапа: сборка зелёная, тесты проходят, коммит с понятным сообщением. Если в требованиях есть неоднозначность, которая реально меняет архитектуру, сначала задай мне вопрос; мелкие решения принимай сам и записывай в `docs/decisions.md`.

## Цель

Бот для двух человек (семья). Человек пишет в Telegram обычным текстом, **любое сообщение уходит в LLM-агента**, и агент сам решает, что делать: сохранить блюдо, сохранить магазинный продукт, записать приём пищи, поправить или деактивировать запись, показать итоги, ответить на вопрос или задать уточняющий вопрос. Отдельных команд для основного сценария нет («съел» не команда, а обычная фраза).

Основной функционал:

1. **Блюдо (рецепт).** Я пишу состав в граммах до готовки, метод приготовления и вес готового блюда. LLM считает КБЖУ и клетчатку всего приготовленного, код делит на вес готового и получает значения на 100 г. После моего подтверждения сохраняется **новая версия** блюда. Через неделю тот же борщ с другим составом даёт ещё одну версию, и в расчётах всегда используется **самая свежая активная**.
2. **Магазинный продукт.** Я один раз называю его КБЖУ (и клетчатку, если есть), LLM разбирает и сохраняет версию на 100 г; дальше продукт находится по названию.
3. **Приём пищи.** «Съел 300 г борща и 150 г творога»: агент находит блюда в памяти, код масштабирует значения по граммам (без вызова LLM) и пишет в дневник.
4. **Итог дня** по каждому человеку отдельно.

**Везде, где есть КБЖУ, есть и клетчатка** (`fiber_g`), но она необязательна: если данных нет, поле просто опускается, это не ошибка и не повод переспрашивать.

## Стек (зафиксирован)

- Java 21, Spring Boot 3.x, **Gradle (обычный Groovy DSL, `build.gradle`)**
- PostgreSQL 16 + расширения `pgvector` и `pg_trgm`
- Миграции: **Liquibase**, changelog в формате **обычного SQL** (formatted SQL, `--liquibase formatted sql`, `--changeset`). Для функций/триггеров на plpgsql ставить `splitStatements:false`.
- Telegram: библиотека `telegrambots` (rubenlagus) со Spring Boot starter, **long polling** (белого IP и домена нет). Только текст, фото и голос не обрабатываем.
- LLM: **LangChain4j**, провайдер Google Gemini (`langchain4j-google-ai-gemini`), ключ из AI Studio, бесплатный уровень. Имена моделей (основная и эмбеддингов) только в конфиге/env, не в коде. Слой LLM спрятать за своим интерфейсом, чтобы провайдера можно было заменить. Агент строится на tool calling (AiServices или аналог).
- Эмбеддинги: модель эмбеддингов Gemini с фиксированной размерностью (например 768), размерность в миграции и в конфиге согласованы; при несовпадении приложение не стартует.
- Тесты: JUnit 5, Testcontainers (Postgres с pgvector, для тестов нужен Docker на машине разработки/CI), LLM в тестах мокается.
- **Деплой, этап 1 (сначала так): без Docker.** PostgreSQL 16 с pgvector установлен отдельно (на хосте или отдельном сервере), приложение запускается как отдельный процесс (`java -jar`, на Ubuntu под systemd). Конфигурация только через env / файл окружения.
- **Деплой, этап 2 (в конце): Dockerfile + `docker-compose.yml` для прода** (app + postgres с pgvector, `restart: unless-stopped`) и GitLab CI (`.gitlab-ci.yml`: build, test, docker image). Приложение не должно зависеть от Docker: те же env-переменные работают в обоих режимах.

## Роль LLM и роль кода

LLM делает то, что требует знаний и суждения:
- понимает свободный текст и выбирает, какие инструменты вызвать (в том числе несколько за один ход);
- считает КБЖУ+клетчатку **всей порции/кастрюли** по составу и методу приготовления, оценивает потери и впитывание масла, учитывает «до и после приготовления»;
- разбирает КБЖУ магазинного продукта из текста;
- выбирает среди кандидатов из памяти, а при сомнении переспрашивает пользователя;
- оценивает вес и состав, если пользователь не указал (с допущениями и уровнем уверенности).

Код делает то, что должно быть детерминированным:
- валидирует всё, что LLM передаёт в инструменты записи;
- считает значения на 100 г (`всё блюдо / вес готового × 100`) и масштабирует **уже известные** значения (на 100 г × граммы), чтобы не платить за вызов LLM и не копить ошибки;
- хранит, суммирует, агрегирует по датам и часовым поясам;
- **дописывает блок «Итого за сегодня» в конец ответа** (не LLM, чтобы цифры не выдумывались).

Данные в инструменты LLM передаёт structured-аргументами (JSON по схеме), свободный текст не парсим.

### Валидация в коде (обязательна, внутри `save_dish`/`log_estimate`)

- Все значения неотрицательны, в разумных диапазонах (пределы в конфиге).
- Проверка Атуотера: `kcal ≈ 4·protein + 9·fat + 4·carbs` (соглашение: `carbs_g` включает `fiber_g`, `fiber_g <= carbs_g`). Допуск по умолчанию ±15 %, настраиваемый. Если клетчатка не указана, проверки по ней пропускаются.
- Для рецепта: вес готового блюда обязателен и должен быть правдоподобным относительно суммы сырых ингредиентов (диапазон в конфиге); значения на 100 г считает код, а не LLM.
- При провале валидации инструмент возвращает LLM текст ошибки, и LLM исправляет вызов сама (в рамках лимита шагов агента). Если не вышло, пользователю показывается результат как «низкая уверенность» с предложением поправить вручную.

## Безопасность данных: ничего не удаляется

- В `app_user`, `dish_version`, `meal_entry` есть `active boolean not null default true` и `deactivated_at timestamptz`. Физических удалений нет.
- **БД-слой:** роль приложения без права `DELETE`; дополнительно триггер, который бросает исключение на любой `DELETE` в этих таблицах. Миграции Liquibase выполняются отдельной ролью-владельцем (отдельные `spring.liquibase.user/password`), приложение работает под ограниченной ролью.
- **Слой инструментов:** у LLM нет tool для удаления, только `deactivate_*`. Нет инструментов для работы с `app_user` вообще: деактивация пользователя делается только вручную (SQL или admin-команда для id из конфига).
- Все запросы читают только `active = true`. Неактивный пользователь, как и чужой telegram_id, игнорируется. Деактивация версии блюда делает «актуальной» предыдущую активную версию.
- `user_id` берётся из контекста Telegram-сообщения, а не из аргументов LLM: экземпляр инструментов создаётся на каждый запрос с уже привязанным пользователем.

## Модель данных (Liquibase SQL, уточни типы и индексы)

- `app_user`: id, telegram_id (unique), name, timezone (по умолчанию `Asia/Almaty`), goal_kcal, goal_protein, goal_fat, goal_carbs, goal_fiber (все nullable), active, deactivated_at. **Whitelist**: список разрешённых telegram_id из конфига + активность.
- `dish_version` (**общая для обоих пользователей**, иммутабельная): id, name, normalized_name, embedding `vector(N)`, kind (`RECIPE` | `PRODUCT`), на 100 г: kcal, protein_g, fat_g, carbs_g, fiber_g (nullable), cooked_weight_g (nullable, для рецептов), source_text (исходное описание рецепта/продукта от пользователя), method (метод приготовления, nullable), confidence, assumptions (text), created_by_user_id, created_at, active, deactivated_at. Версии **не обновляются** (кроме флага деактивации), правка = новая версия. «Актуальная» = самая свежая по `created_at` среди активных версий блюда с тем же названием.
- `meal_entry` (раздельная по пользователям): id, user_id, eaten_at (timestamptz), name, dish_version_id (nullable), grams, **снимок** kcal/protein_g/fat_g/carbs_g/fiber_g на момент записи, confidence, assumptions, created_at, active, deactivated_at. Снимок нужен, чтобы история не менялась при появлении новых версий блюда.
- `chat_message`: id, user_id, role, content, created_at. Память диалога: последние N сообщений и/или за последние X минут идут в контекст агента (так ответы на уточняющие вопросы подхватываются естественно).
- `dish_draft`: черновик новой версии блюда, ожидающий подтверждения кнопкой (payload JSON, user_id, expires_at, статус).
- Индексы: GIN `pg_trgm` по `normalized_name`, HNSW (или IVFFlat) по `embedding`, btree по `(user_id, eaten_at)`, частичные индексы по `active`.

Агрегаты «день» считаются обычным SQL с учётом часового пояса пользователя (`AT TIME ZONE`), без LLM.

## Поиск блюда в памяти (`find_dish`)

1. Кандидаты: точное совпадение `normalized_name` (нормализация: нижний регистр, `ё→е`, trim), затем `pg_trgm` similarity, затем pgvector (top-K по косинусу). Объединить, дедуплицировать по блюду.
2. Для каждого блюда взять самую свежую активную версию.
3. Вернуть LLM кандидатов с названием, видом, датой версии и оценкой схожести; **решение принимает LLM**: выбрать подходящего, при сомнении спросить пользователя (кнопками или текстом). Пороги в конфиге.
4. Если подходящего нет, LLM сообщает об этом и предлагает добавить блюдо, либо записывает приблизительную оценку через `log_estimate` (помечается «приблизительно», в память блюд **не** попадает).

## Инструменты агента (tool calling, один агент, без оркестратора)

| Инструмент | Что делает |
|---|---|
| `find_dish(query)` | Поиск кандидатов (exact + trgm + вектор) |
| `get_dish_versions(dish)` | История версий блюда |
| `save_dish(...)` | Рецепт или продукт: валидация, расчёт на 100 г, создаёт **черновик** (`dish_draft`) и карточку с кнопками «Сохранить» / «Отмена» |
| `log_meal(dish_version_id, grams, eaten_at)` | Масштабирование в коде, запись со снимком значений |
| `log_estimate(name, grams, per_100g…, assumptions)` | Запись по оценке LLM без сохранения в память блюд |
| `update_meal_entry(id, grams / eaten_at / значения)` | Правка своей записи |
| `deactivate_meal_entry(id)` / `deactivate_dish(id)` | Мягкая деактивация |
| `get_day_summary(date)` | Итоги дня этого пользователя |
| `set_goal(...)` | Цели пользователя, включая клетчатку |

Ограничители: максимум 6 вызовов инструментов за ход, rate limit на пользователя, retry при ошибках LLM, все аргументы инструментов валидируются в коде.

**Подтверждение:** новые версии блюд/продуктов сохраняются только после нажатия кнопки (иначе ошибочная версия станет «самой свежей»). Приёмы пищи пишутся сразу и исправляются/деактивируются потом.

## UX в Telegram

- Свободный текст на русском, без обязательных команд: «съел 400 г борща и 2 куска хлеба», «на обед плов, примерно тарелка», «вот рецепт борща: …», «творог Простоквашино 5%: 121 ккал, Б 16, Ж 5, У 3», «не 400, а 300 г», «удали последнюю запись».
- Ответ бота, в зависимости от решения агента:
  - **«Добавил»**: что распознано и записано, КБЖУ + клетчатка по позициям и итог приёма, уровень уверенности и допущения, если оценка приблизительная;
  - **«Уточнение»**: один короткий вопрос (по возможности кнопками). Не больше 1-2 вопросов подряд, иначе оценить с допущениями и пометить низкую уверенность;
  - **Карточка блюда/продукта** для подтверждения с кнопками «Сохранить» / «Отмена» (правка текстом: «убери масло», «готового вышло 4 кг»).
- **Каждый ответ, после которого изменились записи дня** (добавление, правка, деактивация), заканчивается блоком, который формирует код:
  `Итого за сегодня: 1450 ккал · Б 78 · Ж 52 · У 160 · Клетч. 21`
  - считается **для данного пользователя** за текущую дату в его часовом поясе;
  - если заданы цели, добавить остаток: `Осталось: 550 ккал · Б 12 · Ж 8 · У 40 · Клетч. 9` (перебор показывать как `+120`);
  - клетчатка выводится только если по ней есть данные.
- Служебные команды (минимум): `/start`, `/help`, `/today` (итоги дня), `/dishes` (список сохранённых блюд, поиск).
- Язык интерфейса: русский.

## Надёжность и стоимость

- Обработка 429/5xx от Gemini: retry с экспоненциальной задержкой и jitter, затем понятное пользователю сообщение. Не терять сообщение пользователя.
- Каждое сообщение теперь стоит минимум один вызов LLM (с инструментами обычно 2-3): держать промпты короткими, следить за лимитами бесплатного уровня, лимиты запросов на пользователя в конфиге.
- Логировать вызовы LLM и инструментов (модель, токены, латентность, имя инструмента), без персональных данных сверх необходимого.
- Все секреты (Telegram token, Gemini key, whitelist, DB) только через env / файл окружения (в `.gitignore`), в репозитории `.env.example`.
- Бэкап: `scripts/backup.sh` (`pg_dump` в файл с ротацией) и описание в README, как запускать по cron.

## Критерии готовности

- Сохранил «борщ» с одним составом, неделю спустя сохранил другую версию, запрос «съел 300 г борща» использует вторую; старые записи дневника не изменились.
- Магазинный продукт вносится один раз и потом находится по названию, в том числе по похожему («творог простоквашино»).
- Любое сообщение обрабатывается агентом; просьба удалить что-либо приводит только к `active = false`. Тест: `DELETE` из-под роли приложения завершается ошибкой.
- Рецепт без веса готового блюда вызывает уточняющий вопрос, а не молчаливую оценку.
- Клетчатка присутствует в БД, ответах бота и итогах дня, но её отсутствие не ломает расчёты.
- «За день» считается по часовому поясу пользователя; у двух пользователей итоги раздельные.
- Каждый ответ о добавленной еде заканчивается итогом за сегодня (К/Б/Ж/У + клетчатка, если есть) именно этого пользователя.
- Чужой или неактивный telegram_id игнорируется.
- Тесты (включая Testcontainers) проходят; приложение работает как отдельный процесс с отдельной БД без Docker, а затем поднимается через `docker compose up`.
