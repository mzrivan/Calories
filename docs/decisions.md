# Принятые решения

- **Master changelog Liquibase в YAML**, сами миграции — formatted SQL (`db/changelog/sql/*.sql`). Spring Liquibase нужен один корневой файл, `include` подключает SQL.
- **Пользователи**: whitelist в `ALLOWED_TELEGRAM_IDS`; запись в `app_user` создаётся при первом сообщении разрешённого id (имя из Telegram). Деактивация — только вручную SQL (`update app_user set active=false, deactivated_at=now()`); `ON CONFLICT DO NOTHING` не воскрешает деактивированного.
- **Иммутабельность `dish_version`** обеспечивает триггер (разрешено менять только `active`/`deactivated_at`), плюс триггер запрета `DELETE` на `app_user`, `dish_version`, `meal_entry`, `chat_message`.
- **Роли**: `calorie_owner` (миграции), `calorie_app` (приложение: select/insert/update, без delete). Создаются `scripts/db-init.sql`; грант-миграция срабатывает, если роль существует (`runOnChange`).
- **Рецепт**: LLM передаёт итог всего готового блюда + `cookedWeightG` (+ необязательно `rawWeightG` для проверки правдоподобия); на 100 г считает код. Для продукта значения сразу на 100 г.
- **Валидация**: «жёсткие» ошибки (отрицательные, нет веса готового) не принимаются никогда; «мягкие» (Атуотер, диапазоны, отношение веса) возвращаются LLM для исправления, после `max-validation-retries` (2) принимаются с `LOW` и пометкой в допущениях. Черновик блюда в любом случае требует подтверждения кнопкой.
- **Деактивация блюда** — по id версии. Актуальная версия = самая свежая активная с тем же `normalized_name`.
- **Правка черновика текстом** = новый вызов `save_dish`; старый ожидающий черновик получает статус `SUPERSEDED`.
- **Повтор запроса к LLM** при ошибках (429/5xx) делается только пока в этом ходе не было записей, чтобы не продублировать их.
- **Итоги дня** выводятся блоком от кода после любого хода, где менялись записи, и после `get_day_summary` за сегодня / `set_goal`.
- **Подтверждение кнопкой** обходит LLM; отмена — пересылкой сообщения бота и следующей командой или ответом на исходное сообщение. Простые «удали/отмени/отмена» деактивируют связанные записи без LLM, правки и неясные запросы передаются агенту с точными id. Результат записывается в `chat_message`.
- **Связь сообщений и записей** хранится в `bot_message`, временный выбор после пересылки — в `bot_message_selection` (15 минут, привязка к пользователю и чату). Telegram не передаёт исходный message_id для пересылок из личного чата: сопоставляем точный текст только среди сообщений этого пользователя и отказываемся угадывать при разных наборах id. Блок итогов не добавляет записи в область отмены.
- Версии зависимостей: Spring Boot 3.4.5, LangChain4j 1.23.0, telegrambots 8.3.0.

## Архитектура разбора сообщений (меньше LLM)

- **Порядок обработки**: команды → `IntentParser` (вес, шаги, профиль, цель `цель N`, итоги, баланс) → `MealTextParser` (список «блюдо + вес») → LLM-агент. Каждый шаг консервативен: при неоднозначности (`83 творог 0.1 йогурт 40 1.5`, `сухие 172 готовые 440`, скобки/КБЖУ в тексте, позиция без веса) весь текст уходит агенту, а не записывается наугад.
- **pgvector удалён**: векторный поиск был избыточен. Поиск блюда — `DishMatcher`: точное `normalized_name` → таблица `dish_alias` → `pg_trgm` (`greatest(similarity, word_similarity)`). `EXACT` = имя/алиас; `APPROX` = trgm ≥ `approx-threshold` (0.5) с отрывом `approx-gap` (0.1) от второго кандидата; иначе `UNKNOWN`.
- **Подтверждение**: все позиции `EXACT` пишутся сразу одной пачкой (`meal_entry.batch_id`); есть `APPROX` или оценка LLM → `meal_draft` (jsonb, TTL как у черновиков блюд) + кнопка «Записать». При подтверждении `APPROX` код запоминает алиас. Кнопки отмены больше не отправляются, обработчики старых callback сохранены.
- **Незнакомые блюда** — один структурный запрос `AgentLlm.estimate(...)` на всю пачку (без инструментов и истории). Ответ валидируется `NutritionValidator`; hard-ошибки — позиция не записывается, soft — `LOW` + пометка. Оценки ИИ сохраняются как новые `dish_version` (`PRODUCT`, `method='LLM'`, уверенность не выше `MEDIUM`) только после подтверждения; при сбое LLM ничего не записывается.
- **Справочник**: миграция 004 (`db/seed/products.csv`, `aliases.csv`, Liquibase `loadData`), `dish_version.created_by_user_id = NULL` — системные записи. Значения ккал в CSV согласованы с формулой Атуотера (тест `SeedProductsTest` прогоняет их через `NutritionValidator`).
- **Время приёма пищи** в списках — «сейчас»; сообщения с датой/временем разбирает агент.

## Расход калорий

- Профиль (`app_user.height_cm`, `birth_year`, `sex`) вводится текстом один раз; возраст хранится как год рождения (`год дня − birth_year`).
- Формулы (`EnergyCalculator`, коэффициенты в `app.energy.*`):
  - BMR (Миффлин–Сан-Жеор): `10·кг + 6,25·см − 5·возраст + 5 (М) / −161 (Ж)`;
  - обмен с надбавкой: `BMR × tef-factor` (1,1 — термический эффект пищи и бытовая активность);
  - шаги: длина шага = `рост × 0,415`, ккал = `0,5 × кг × км` (чистый расход ходьбы);
  - всего = обмен + шаги. Это оценка, а не измерение.
- `daily_activity` — одна строка на `(user_id, day)`: вес и шаги обновляются частично и сколько угодно раз за день, расчётные `bmr/steps/total` пересчитываются и сохраняются при каждой записи. Вес дня, если не вводился, берётся последний известный.
- Баланс = съедено − потрачено (минус = дефицит). Нет профиля/веса — вместо числа подсказка, что написать; нет шагов — расход помечается неполным.
